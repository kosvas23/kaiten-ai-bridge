# Проверки и границы приёмки

Дата последней локальной проверки: 03.09.2026.

## Что проверено автоматически

Набор тестов покрывает основные сценарии ТЗ на уровне приложения и контрактных
адаптеров:

- надёжная очередь до ответа webhook, дедупликация, порядок комментариев одной
  карточки, восстановление более раннего комментария при webhook не по порядку и
  параллельность разных карточек;
- безусловный приоритет незавершённого `card:add` перед комментариями той же
  карточки, даже если `comment:add` пришёл первым или получил более ранний
  timestamp;
- первоначальная отправка, исправление отклонённой заявки новым комментарием,
  отсутствие повторной отправки после принятого `job_id` и перенос только после
  подтверждения;
- первоначальный Service Desk-комментарий и его файлы сохраняются даже при
  совпадении автора с API-пользователем, при этом отдельный `comment:add` этого
  описания и обычные комментарии технического аккаунта не создают цикл;
- динамические custom fields и новые select-значения, безопасный fallback для
  новых стандартных/неизвестных полей, отсутствие email и внутренних user ID в
  промпте;
- all-or-nothing проверка расширений и 5 MiB, дедупликация файлов, стабильный
  JSON, Base64, checksum и немедленное удаление временной копии;
- legacy/restricted file routes без передачи Kaiten Bearer на файловое хранилище;
- `202 + job_id`, `Idempotency-Key`, тайм-ауты и ограничения размера тела;
- callback Bearer, schema/status validation, дедупликация `result_id`, публикация
  до ответа `2xx` и отказ от несогласованных файлов результата;
- девять повторов, технический статус, контрольная сверка, восстановление после
  перезапуска SQLite, 29/30-дневный lifecycle и очистка более 100 карточек;
- минимальная схема SQLite, отсутствие пользовательского содержимого в базе и
  безопасный allowlist технических полей журналов;
- потоковое ограничение входящего тела, health/live и очистка успешных/ignored
  ключей, callback-ключей, временных файлов и ротированных журналов.

Последний полный локальный прогон: `171 passed`, суммарное покрытие исходного
кода — 87%. Дополнительно успешно прошли `ruff check`, проверка форматирования,
компиляция модулей, `pip check` и сборка wheel.

- карточка через Kaiten API подтверждённо перемещена в колонку `В работе`;
- токен Kaiten в исходящем JSON отсутствует, очередь после теста пуста.

После исправления порядка webhook карточка `69599497`, у которой `comment:add`
пришёл перед `card:add`, была автоматически восстановлена из SQLite: начальная
заявка успешно отправлена, отдельное исходное описание проигнорировано без
дублирования, служебный комментарий не создал цикл, очередь вернулась к нулю.

В этом тесте корпоративная ИИ была заменена локальным HTTP-получателем. Входящий
callback и публикация ответа обратно в Kaiten ещё не проверялись сквозным тестом.

## Что ещё не является пройденной production-приёмкой

- интеграция с реальным endpoint корпоративной ИИ и подписанной JSON-схемой;
- обратные файлы callback;
- сквозной callback на выделенной тестовой карточке с публикацией результата;
- установка, reboot/recovery, hardening и нагрузочная проверка на выбранной
  версии Ubuntu;
- сборка контейнера на текущей рабочей машине: Docker здесь не установлен;
- строгая exactly-once публикация callback через аварийное окно между Kaiten и
  SQLite без дополнительного идемпотентного механизма.

Эти пункты не скрыты за значением «готово»: они соответствуют решениям из
`OPEN_DECISIONS.md` и должны закрываться владельцами инфраструктуры, Kaiten и
корпоративной ИИ перед рабочим включением webhook.
