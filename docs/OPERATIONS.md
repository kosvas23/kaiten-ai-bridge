# Эксплуатация Kaiten AI Bridge

Эти материалы являются шаблонами подготовки развёртывания, а не подтверждением готовности production. До первого рабочего запуска необходимо закрыть решения из [OPEN_DECISIONS.md](OPEN_DECISIONS.md), проверить актуальную Ubuntu и согласовать HTTP-контракт с корпоративной ИИ.

## Сетевая схема

- Kaiten вызывает только публичный HTTPS webhook `https://bridge.example.com/webhooks/kaiten` через nginx.
- Приложение по умолчанию слушает `127.0.0.1:8080`; сам порт `8080` не публикуется в интернет.
- Callback корпоративной ИИ направляется напрямую на `http://127.0.0.1:8080/callbacks/corporate-ai` и должен содержать отдельный Bearer-токен.
- Исходящий запрос к корпоративной ИИ по предварительной конфигурации направляется на `http://127.0.0.1:8090/api/v1/jobs`.
- Приложение обращается к Kaiten по HTTPS через версионированный base URL `https://tagat.kaiten.ru/api/v1`.

Имена, порты и пути выше являются настраиваемыми. Публичными в firewall должны оставаться только необходимые `80/tcp` и `443/tcp`; порт приложения и временный сетевой порт ИИ нельзя открывать до согласования авторизации и сетевой схемы.

## Конфигурация и секреты

Полный перечень переменных находится в `.env.example`. Скопируйте его в отдельный эксплуатационный env-файл и замените все значения в угловых скобках. В репозиторий этот файл не добавляется.

Для systemd используется `/etc/kaiten-ai-bridge/bridge.env`, владелец `root:root`, режим `0600`. Для Compose используется локальный `.env` с режимом `0600`. Не передавайте env-файл в журналы, тикеты или диагностику. Токены Kaiten, исходящего API и callback должны быть разными и ротироваться независимо.

Относительные пути из `.env.example` не используются в systemd-шаблоне: состояние хранится в `/var/lib/kaiten-ai-bridge`, журналы — в `/var/log/kaiten-ai-bridge`, временные файлы — в закрытом подкаталоге состояния. Kaiten base URL намеренно закреплён на `/api/v1`; переход на другую версию требует проверки адаптера.

Перед production обязательно задайте `BRIDGE_MAX_OUTGOING_BODY_BYTES`. Значение должно совпадать с лимитами корпоративной ИИ и всех прокси и учитывать увеличение файлов при Base64-кодировании.

## Вариант systemd

Шаблон рассчитан на установленный Python 3.11 или новее и отдельную системную учётную запись без shell. Команды установки пакетов ОС зависят от ещё не выбранной версии Ubuntu.

1. Создайте пользователя: `sudo useradd --system --home-dir /var/lib/kaiten-ai-bridge --shell /usr/sbin/nologin kaiten-ai-bridge`.
2. Создайте `/opt/kaiten-ai-bridge`, установите туда проверенный release-артефакт и виртуальное окружение `/opt/kaiten-ai-bridge/.venv`. Console script должен находиться по пути `/opt/kaiten-ai-bridge/.venv/bin/kaiten-ai-bridge`.
3. Установите env-файл: `sudo install -o root -g root -m 0600 .env /etc/kaiten-ai-bridge/bridge.env`.
4. Установите unit: `sudo install -o root -g root -m 0644 deploy/kaiten-ai-bridge.service /etc/systemd/system/kaiten-ai-bridge.service`.
5. Проверьте доступность путей и переменных, затем выполните `sudo systemctl daemon-reload` и `sudo systemctl enable --now kaiten-ai-bridge`.
6. Проверьте `systemctl status kaiten-ai-bridge` и `journalctl -u kaiten-ai-bridge --since today`.

`StateDirectory` и `LogsDirectory` создают закрытые каталоги с нужным владельцем. Unit запускается без capabilities, ограничивает доступ к файловой системе и автоматически перезапускает процесс. Совместимость директив hardening необходимо проверить командой `systemd-analyze security kaiten-ai-bridge.service` именно на целевой версии systemd; неизвестные старой версии директивы следует разбирать до запуска, а не удалять вслепую.

## Вариант Docker Compose

1. Выполните `cp .env.example .env`, заполните решения и секреты, затем установите режим `chmod 600 .env`.
2. Проверьте итоговую конфигурацию без публикации её вывода: `docker compose config --quiet`.
3. Соберите образ: `docker compose build --pull`.
4. Запустите сервис: `docker compose up -d`.
5. Проверьте `docker compose ps` и `docker compose logs --since 10m bridge`.

Контейнер работает от UID/GID `10001`, с read-only root filesystem, без Linux capabilities и с отдельными томами для SQLite, журналов и временных файлов. Compose использует `network_mode: host`, доступный на целевой Ubuntu: это сохраняет семантику `127.0.0.1` для nginx и корпоративной ИИ на том же сервере. Если корпоративная ИИ также контейнеризирована, перед production следует выбрать общую закрытую сеть и скорректировать адреса; смешивать оба режима без сетевого теста нельзя.

Не запускайте systemd- и Compose-варианты одновременно с одной базой или одним HTTP-портом.

## nginx и TLS

1. Скопируйте `deploy/nginx.example.conf` в `/etc/nginx/conf.d/kaiten-ai-bridge.conf`.
2. Замените `bridge.example.com` и пути сертификата, выпустите сертификат доверенного центра и настройте его автоматическое продление.
3. Выполните `sudo nginx -t`, затем `sudo systemctl reload nginx`.
4. Настройте в Kaiten точный URL `https://<имя>/webhooks/kaiten` только после проверки DNS, TLS и firewall.

Пример проксирует наружу только webhook; `/health` и callback через публичный virtual host возвращают `404`. Логи nginx тоже подпадают под трёхдневный срок: настройте системный `logrotate` на ежедневную ротацию и хранение не более трёх архивов либо отключите access log для этого virtual host после согласования с эксплуатацией.

## Проверка перед включением webhook

1. Убедитесь, что `GET http://127.0.0.1:8080/health` возвращает структурированный JSON. Состояние `degraded` требует устранить недоступность Kaiten или получателя.
2. Проверьте исходящий HTTPS к `tagat.kaiten.ru` из того же execution environment.
3. Проверьте доступность согласованного endpoint корпоративной ИИ и отсутствие токенов в выводе.
4. С внешней тестовой сети проверьте сертификат и то, что публичен только точный webhook-путь.
5. Проведите end-to-end тест на отдельной тестовой карточке: один `card:add`, один публичный комментарий, повтор webhook и повтор callback с тем же `result_id`.
6. Убедитесь, что карточка переходит в `В работе` только после `202` с `job_id`, а дубли не создают повторных сообщений.
7. Перезапустите выбранный runtime во время ожидающего события и подтвердите восстановление SQLite-очереди.

Не отправляйте искусственный webhook с production `card_id`: он может привести к реальному исходящему заданию и изменению карточки.

## Мониторинг

Health endpoint должен показывать состояние процесса, доступность Kaiten и получателя, последний webhook, последнюю сверку и очистку, а также размеры ожидающей и ошибочной очереди. Рекомендуемые проверки:

- процесс или контейнер запущен;
- health доступен только локальному мониторингу;
- `pending_events`, `error_events` и `queue_size` не растут постоянно;
- `last_reconciliation_at` обновляется не реже одного раза за шесть часов;
- `last_cleanup_at` обновляется раз в сутки;
- свободное место тома SQLite и временного каталога имеет запас;
- TLS-сертификат не приближается к окончанию срока.

Не включайте тело JSON, промпты, комментарии, Base64, ссылки на скачивание или env в сбор диагностических данных. Для systemd используйте `journalctl -u kaiten-ai-bridge`; для Compose — `docker compose logs bridge`. Срок хранения технических журналов — не более трёх календарных дней.

## Резервное копирование и восстановление SQLite

SQLite содержит только минимальные технические идентификаторы, но резервную копию всё равно храните как конфиденциальную. Для простой согласованной копии остановите выбранный runtime, дождитесь корректного завершения, скопируйте `bridge.sqlite3` в закрытое хранилище и сразу запустите runtime снова. Не копируйте только основной файл при работающем процессе: актуальные транзакции могут находиться в WAL.

Для восстановления остановите runtime, сохраните текущие файлы базы как отдельный инцидентный снимок, установите проверенную копию с владельцем `kaiten-ai-bridge` и режимом `0600`, затем запустите сервис и проверьте health и дедупликацию. Срок хранения резервных копий и место шифрования должны быть отдельно согласованы: резервная копия не должна обходить 30-дневное удаление связей.

## Обновление и откат

Перед обновлением зафиксируйте версию, сделайте согласованную копию SQLite и сохраните предыдущий wheel или digest образа. Для systemd остановите unit, установите новый release в виртуальное окружение и запустите unit. Для Compose используйте неизменяемый versioned tag/digest вместо `local`, затем пересоздайте только сервис bridge.

После обновления проверьте health, восстановление ожидающих событий, права каталогов и отсутствие изменений схемы данных без миграционного плана. При откате остановите runtime, восстановите совместимую версию приложения и — только если новая версия меняла схему — соответствующую согласованную копию базы. Не удаляйте SQLite и тома ради отката.

## Реакция на инциденты

- При недоступности Kaiten или ИИ оставьте очередь на диске, ограничьте повторные рестарты и устраняйте сетевую причину; не очищайте событие вручную.
- При заполнении диска сначала остановите приём через nginx, затем сохраните состояние и освободите место вне каталога SQLite. Не удаляйте WAL работающей базы.
- При компрометации токена отключите соответствующий маршрут, отзовите и замените только этот токен, перезапустите runtime и проверьте журналы на отсутствие секретов.
- При повторных комментариях не редактируйте базу вручную: сохраните снимок, зафиксируйте `card_id`, `comment_id`, `job_id` и `result_id` без пользовательского содержимого и расследуйте идемпотентность обеих сторон.
