## Задача проекта

Программная прослойка связывает Kaiten и корпоративную ИИ:

1. Принимает внешний webhook Kaiten.
2. Сохраняет технический идентификатор события в надёжной SQLite-очереди.
3. Повторно читает актуальную карточку, комментарии и файлы через Kaiten API.
4. Формирует детерминированный JSON с Markdown-промптом и файлами Base64.
5. Отправляет JSON корпоративной ИИ и ожидает `202 Accepted + job_id`.
6. Принимает асинхронный callback и публикует результат в исходной карточке.

## Исправленные пограничные ошибки

### Автор исходного Service Desk-описания совпадает с API-пользователем

Проблема обнаружена на карточке `69598323`. Kaiten атрибутировал исходный
`sd_description` тому же пользователю, чей API-токен использует bridge. Старый
фильтр считал описание техническим и исключал вместе с ним прикреплённый файл.

Исправленное поведение:

- начальное `sd_description` включается независимо от автора
- приложенные к нему файлы также включаются
- отдельное `comment:add` этого описания игнорируется как
  `initial_service_comment`, потому что содержимое уже вошло в начальную заявку
- остальные комментарии API-пользователя по-прежнему считаются техническими

Таким образом пользовательское исходное описание не теряется, а комментарии,
которые прослойка сама публикует через API, не создают цикл.

### `comment:add` поступает раньше `card:add`

Проблема обнаружена на карточке `69599497`: события имели одинаковое исходное
время, но комментарий был записан первым и блокировал начальную заявку.

Теперь незавершённый `card:add` всегда имеет приоритет внутри своей карточки,
даже если `comment:add` пришёл раньше или имеет такое же/более раннее исходное
время. После исправления застрявшая заявка была обработана, технический
комментарий проигнорирован, очередь вернулась к нулю. Поведение дополнительно
подтверждено новым E2E на карточке `69600162`.

## Как безопасно снова поднять локальный стенд

Сначала проверить, что порты свободны и неизвестные процессы не будут затронуты:

```powershell
Get-NetTCPConnection -State Listen -LocalPort 8080,8090 -ErrorAction SilentlyContinue
```

Затем:

1. Загрузить `KAITEN_BASE_URL` и `KAITEN_TOKEN` из `kaiten.env` только в
   окружение процесса и сопоставить их с `BRIDGE_KAITEN_BASE_URL` и
   `BRIDGE_KAITEN_TOKEN`. Не выводить значения.
2. Остальные настройки взять из [.env.example](.env.example) и таблицы ID выше.
3. Для локального теста установить:
   - `BRIDGE_ENVIRONMENT=development`
   - `BRIDGE_AI_HOST=127.0.0.1`
   - `BRIDGE_AI_PORT=8090`
   - `BRIDGE_AI_PATH=/api/v1/jobs`
   - новый случайный `BRIDGE_AI_BEARER_TOKEN`, одинаковый для bridge и capture
   - `BRIDGE_RECONCILE_ON_STARTUP=false`
   - `BRIDGE_DATABASE_PATH=data/run/bridge.sqlite3`
   - `BRIDGE_LOG_DIR=data/run/logs`
   - `BRIDGE_TEMP_DIR=data/run/tmp`
   - `BRIDGE_CAPTURE_DIR=data/captures`
4. В отдельных длительных терминальных сессиях запустить:

```powershell
.\.venv\Scripts\python.exe -m kaiten_ai_bridge.capture
.\.venv\Scripts\python.exe -m kaiten_ai_bridge
.\.tools\cloudflared.exe tunnel --url http://127.0.0.1:8080 --no-autoupdate
```

5. Проверить локальные endpoints:

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:8080/health'
Invoke-RestMethod -Uri 'http://127.0.0.1:8080/live'
Get-NetTCPConnection -State Listen -LocalPort 8080,8090
```

6. Взять **новый** URL из вывода `cloudflared`, проверить `<new-url>/live`, затем
   установить `<new-url>/webhooks/kaiten` в External Webhook Kaiten.

Файл `.tools/cloudflared.exe` уже загружен из официального GitHub release
Cloudflare. Версия `2026.8.3`, digest ранее сверялся с GitHub API; `.tools`
исключён из Git.

Не завершать процессы без проверки PID и не убивать неизвестный процесс,
занимающий порт.

## Проверка следующей заявки

После запуска стенда и обновления webhook URL пользователь может создать новую
тестовую карточку на `Доске агента` в колонке `Очередь`, с service `ИИ` и
заполненным полем `Тип заявки`.

После получения события:

1. Проверить `/health`, технические логи в `data/run/logs` и очередь без вывода
   токенов или пользовательского содержимого.
2. Найти новый `data/captures/card-*-initial-*.json`.
3. Проверить `schema_version`, `event_type`, `card.id`, `request_type`, секции
   prompt и число файлов.
4. Декодировать каждый `content_base64`, проверить размер и SHA-256.
5. Через read-only Kaiten API подтвердить переход карточки из `Очереди` в
   `В работе`.
6. Открыть пользователю именно фактически перехваченный JSON.

Успешный ответ тестового receiver имеет реальное последствие: bridge переносит
карточку в `В работе`. Не использовать рабочую карточку для destructive E2E без
явного согласия пользователя. Не создавать, не перемещать и не удалять объекты
Kaiten самостоятельно, если пользователь не попросил конкретную мутацию.

## Probe и полный E2E — не одно и то же

`data/probes/card-69416673.json` сформирован реальным Kaiten-клиентом и общими
функциями построения JSON, но команда `probe` намеренно обходит webhook, SQLite,
worker и HTTP receiver. Такой файл подходит для read-only проверки экстракции,
но его нельзя выдавать за результат полного сквозного теста.

## Незакрытые production-вопросы

- реальный URL и подписанный контракт корпоративной ИИ
- формат файлов в callback
- строгая exactly-once гарантия для аварийного окна публикации callback
- постоянный домен, TLS, reverse proxy и защита публичного webhook
- установка и проверка перезапуска на Ubuntu
- отдельная тестовая карточка или среда для destructive E2E
