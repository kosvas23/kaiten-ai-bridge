# Kaiten AI Bridge

Постоянно работающая программная прослойка между пространством Kaiten `ИИ` и
корпоративной ИИ. Сервис не содержит собственной ИИ-модели: он принимает только
технические webhook-триггеры, повторно читает актуальные данные через Kaiten API,
детерминированно формирует JSON с Markdown-промптом и файлами Base64, получает
`202 Accepted` с `job_id`, а затем публикует асинхронный текстовый callback в
исходную карточку.

## Что реализовано

- durable SQLite-очередь до ответа webhook `2xx`;
- `card:add` и публичные человеческие `comment:add`, строгий порядок внутри
  карточки и параллельность разных карточек;
- динамическое чтение custom properties, select/catalog/user справочников;
- legacy и restricted Kaiten files, лимит/whitelist и all-or-nothing проверка;
- детерминированный prompt и исходящий JSON без постоянного хранения содержимого;
- `202 + job_id`, идемпотентные ключи и перенос `Очередь → В работе`;
- идемпотентный callback по `result_id` с публикацией текста в Kaiten;
- повторы, шестичасовая контрольная сверка, ежедневная очистка;
- предупреждение через 29 дней и завершение через 30 дней без активности;
- `/live` и конфигурируемый `/health`;
- запуск через systemd или Docker, reverse-proxy пример для nginx.

## Быстрый локальный запуск

Требуется Python 3.11+.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
cp .env.example .env
```

Задайте секреты из `.env` в окружении процесса (файл `.env` намеренно не
загружается приложением автоматически), затем:

```bash
kaiten-ai-bridge
```

Для тестов и статической проверки:

```bash
pytest
ruff check .
```

## Read-only выгрузка одной карточки

Для проверки экстракции без webhook, получателя и изменений в Kaiten задайте
обычные `BRIDGE_KAITEN_*` параметры и политику файлов, затем выполните:

```bash
kaiten-ai-bridge-probe --card-id 69416673 --output data/probes/card-69416673.json
```

Команда использует только чтение Kaiten и скачивание вложений, формирует точный
предварительный JSON `initial`, записывает его атомарно с закрытыми правами и
печатает только безопасную техническую сводку. Файл содержит пользовательские
данные и Base64, поэтому каталог `data/` исключён из Git; после проверки файл
следует удалить.

Для полного локального теста вместо настоящей корпоративной ИИ можно запустить
loopback-приёмник:

```bash
kaiten-ai-bridge-capture
```

Он слушает `127.0.0.1:8090`, требует тот же `BRIDGE_AI_BEARER_TOKEN`, отвечает
`202 + job_id` и сохраняет фактически полученный JSON в `data/captures`. Такой
тест запускает обычную очередь и worker прослойки и после успешного приёма
перемещает тестовую карточку из `Очереди` в `В работе`.

## Конфигурация

Все параметры имеют префикс `BRIDGE_`. Полный пример находится в
[`.env.example`](.env.example). Для production фиксируйте Kaiten API на `/api/v1`,
не храните токены в репозитории и передавайте их через systemd `EnvironmentFile`,
Docker secrets или защищённое хранилище ОС.

Наблюдаемые на дату ТЗ идентификаторы вынесены в конфигурацию:

- space `834556`;
- board `1868751`;
- `Очередь` `6467479`;
- `В работе` `6467480`;
- `Готово` `6467481`;
- Service Desk service `9162`;
- routing property `Тип заявки` (`626883` в текущем tenant probe).

Варианты `ТКП`, `Запрос` и будущие значения поля не зашиты в код.

## Архитектура

```text
Kaiten webhook
      │ technical IDs only
      ▼
FastAPI ── durable enqueue ──► SQLite
                                  │ per-card ordered workers
                                  ▼
Kaiten REST ──► normalize/validate/build JSON ──► Corporate AI
      ▲                                             │ 202/job_id
      │                                             │ async callback
      └──── public result comment ◄─────────────────┘
```

В SQLite отсутствуют тела webhook/callback, промпты, поля, комментарии, имена и
содержимое файлов, Base64, email и временные URL. Временные файлы создаются с
закрытыми правами, удаляются после попытки и никогда не попадают в журналы.

## Осознанные границы первого этапа

Файлы результата callback пока отклоняются `422`: ТЗ не определяет их формат
(Base64, ссылка или иной способ) и контракт загрузки в Kaiten. Текст callback
поддерживается в пределах документированного лимита комментария Kaiten — 4096
символов. Точные адреса/схемы корпоративной ИИ, авторизация, общий размер JSON и
правила callback retry должны быть подтверждены до production; весь перечень
зафиксирован в `docs/OPEN_DECISIONS.md`.

Обычный повтор callback с тем же `result_id` дедуплицируется. Для строгой
гарантии «ровно один комментарий» при аварии в узком промежутке между успешной
публикацией в Kaiten и фиксацией результата в SQLite нужен согласованный
идемпотентный механизм на стороне Kaiten/получателя; этот production gate также
зафиксирован в открытых решениях.
